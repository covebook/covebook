# ADR-0002: 인앱결제 설계 결정 (상품 유형, 장부, 계정 연결, 실패 처리, 해외 확장)

- 상태: 제안 (정환 확인 후 "승인"으로 변경)
- 날짜: 2026-11-18
- 결정자: 범수, 정환
- 앞선 결정: [ADR-0001](0001-iap-server-go.md) (Go 서버, `go-iap`, 스토어 재조회)
- 이어지는 결정: [ADR-0003](0003-iap-compliance.md) (법규 대응: 고지, 동의, 해지, 기록)
- 가격은 이 문서에서 다루지 않음. 결제 계획 보고(팀 안에서만 공유)에 있음

## 1. 배경

- ADR-0001은 "어디에, 무엇으로 만드는가"만 정했음
- 구현을 시작하려면 상품 유형, 테이블, 계정 연결, 실패 처리 방식이 먼저 정해져야 함
- 2026-11-18에 영어권·중국어권 자료를 조사해 갈림길마다 하나씩 고름
- 자료 대부분은 결제 대행사 문서, 개발자 포럼, 개인 블로그. 공식 문서로 확인한 것과 아닌 것을 부록 A에 구분

## 3. 결정과 근거

### D1. 추가 선반은 소모성 상품

- 선택지
  - A. 비소모성: 스토어가 복원해 줌. 계정당 한 번만 구매 가능
  - B. 소모성: 여러 번 구매 가능. 스토어 복원 없음
  - C. 기간제: 1년 뒤 만료
- 결정: B
- 근거
  - 선반은 1칸, 3칸으로 팔고 여러 번 살 수 있어야 함. 비소모성은 같은 상품을 두 번 못 삼
  - A로 하려면 "연도 × 칸 번호"마다 상품을 따로 등록해야 함. 해마다 등록·심사가 반복됨
  - C는 지난 해 책장의 선반이 사라져 "해마다 기록" 컨셉과 어긋남. 구글에는 기간제 유형이 없어 서버에서 흉내 내야 함
- 감수하는 것
  - 스토어의 "구매 복원"으로는 선반이 돌아오지 않음. 서버 계정이 유일한 기록
  - 애플 심사에서 "영구 상품은 비소모성이어야 한다"는 지적이 나온 사례가 있음. 반대로 소모성으로 바꿔 통과한 사례도 있음. 결과가 갈림
- 대응
  - 선반 구매 기록은 계정에 묶어 서버에 보관. 로그인하면 어느 기기에서든 복원
  - 심사 메모에 "선반은 계정에 기록되고 로그인으로 복원된다"고 적음
  - 반려되면 A로 전환. 호출부를 인터페이스 뒤에 둬서 상품 ID만 바꾸면 되게 함
- 정환 확인: "최대 3칸"이 연도 책장마다인지 계정 전체인지

- 재검토 필요 (2026-11-19): 구글은 소비한 구매를 스토어에서 다시 조회할 수 없어 복원이 서버 기록에만 의존함. 한 번 사면 영구인 상품은 비소모성으로 등록하는 것이 일반 권고. 선반을 비소모성 여러 개로 바꿀지는 선반 범위(이슈 #6)와 함께 정함. 근거: [조사 종합 8-2 T6](../reports/2026-11-19-iap-pitfalls.md)

### D2. 구독은 권한 하나

- 결정: 권한 이름 `plus` 하나. 월·연 상품 모두 같은 권한을 줌
- 애플: 구독 그룹 1개에 월·연 상품. 구글: 구독 1개에 기본 요금제 2개
- 근거: 같은 그룹 안에서는 월↔연 전환을 스토어가 처리함. 서버는 "권한이 있는가"만 판단

### D3. 권한의 기준은 서버 DB

- 결정: 서버가 "이 계정에 `plus`가 있는가, 선반이 몇 칸인가"를 가짐. 앱은 받아서 캐시
- 근거
  - 앱에만 두면 기기 변경, 환불, 다른 플랫폼 로그인을 처리할 수 없음
  - 조사한 자료 대부분이 같은 구조를 권함: 서버가 기준, 앱은 임시 상태
- 앱 동작: 실행할 때와 결제 직후에 서버에서 권한을 받아 옴. 오프라인이면 마지막 캐시 사용

### D4. 권한 갱신 경로는 세 가지

- 결정
  1. 앱이 결제 직후 거래를 서버에 제출
  2. 스토어 알림(애플 V2, 구글 RTDN) 수신
  3. 하루 1회 대조: 곧 만료되는 구독과 최근 알림 내역을 스토어에 다시 조회
- 세 경로 모두 받은 내용을 믿지 않고 스토어 재조회 후 반영 (ADR-0001)
- 근거
  - 1만 있으면 유저가 앱을 다시 안 열 때 갱신·환불을 모름
  - 2만 있으면 알림을 놓쳤을 때 복구가 안 됨. 애플은 실패한 알림을 며칠간 몇 번만 다시 보냄
  - 중국어권 자료가 "알림은 보조, 주기적 조회가 있어야 누락(掉单)을 메운다"고 반복해서 지적
- 구글 알림은 "상태가 바뀌었다"만 알려 줌. 최종 상태는 API로 조회해야 함 (공식 문서)
- 구글 알림은 도착 순서가 보장되지 않음. 알림의 사건 시각으로 최신 여부를 판단하거나, 순서와 무관하게 재조회 결과로 덮어씀 (국내 구현 사례)

### D5. 테이블 4개

| 테이블 | 한 줄의 단위 | 주요 열 |
|---|---|---|
| 거래 | 거래 1건 | 결제 경로, 거래 ID, 원 거래 ID, 상품 ID, 사용자, 환경, 상태, 구매 시각, 통화, 금액, 판매 국가 |
| 구독 | 구독 한 줄기 | 결제 경로, 원 거래 ID(구글은 구매 토큰), 사용자, 상품 ID, 만료 시각, 상태, 자동 갱신 여부, 유예 종료 시각 |
| 알림 기록 | 받은 알림 1건 | 결제 경로, 알림 ID, 종류, 원문, 처리 결과, 받은 시각 |
| 상품 | 파는 상품 1개 | 결제 경로, 상품 ID, 종류(구독·선반), 주는 권한 또는 칸 수 |

- 권한은 따로 저장하지 않고 위 표에서 계산
  - `plus`: 구독 표에 유효한 줄이 있는가
  - 선반 칸 수: 거래 표에서 환불 안 된 선반 거래의 합
- 근거: 권한을 따로 저장하면 원장과 어긋날 수 있음. 규모가 작아 계산 비용은 문제가 안 됨
- 알림 원문을 남기는 이유: 분쟁과 버그 추적

### D6. 중복 방지 키

- 거래: (스토어, 거래 ID) 유일
- 구독: (스토어, 원 거래 ID) 유일. 갱신마다 거래 ID는 새로 생기므로 구독 줄기는 원 거래 ID로 묶음
- 알림: (스토어, 알림 ID) 유일. 같은 알림이 다시 와도 한 번만 처리
- 구글: 구독을 다시 시작하거나 요금제를 바꾸면 구매 토큰이 새로 나옴. 이전 토큰(`linkedPurchaseToken`)을 따라가 같은 줄기로 이음

### D7. 계정 연결 값

- 문제: 애플 `appAccountToken`은 UUID만 받음. 우리 사용자 ID는 정수(BIGINT)
- 결정: 사용자마다 결제용 UUID 1개를 발급해 저장. 애플에는 그 UUID, 구글 `obfuscatedAccountId`에도 같은 값
- 근거
  - 구글은 이 값에 이메일 같은 개인정보를 넣으면 구매를 막음 (공식 문서). 무작위 UUID라 해당 없음
  - 사용자 ID를 그대로 넘기지 않아 내부 번호가 노출되지 않음
- 검증: 스토어 조회 결과의 값이 요청한 계정의 UUID와 다르면 지급 거부

### D8. 스토어 계정 하나, 앱 계정 여럿

- 문제
  - 애플은 Apple ID 하나에 구독 그룹당 구독 하나만 허용
  - `appAccountToken`이 첫 구매 때 굳는지는 불확실. 포럼 관측이 엇갈리고(2023: 처음 값 유지, 2026: 교차 변경 때 바뀜) 애플 문서에는 그런 문장이 없음
  - 2025-06에 값을 나중에 넣거나 바꾸는 API(Set App Account Token)가 생김. 구독을 옮길 때 쓸지는 이슈 #29에서 결정
  - 우리는 앱을 다시 깔면 기기 계정이 새로 생김. "첫 계정에만 귀속"으로 하면 돈 낸 유저가 잠김
- 결정: "구매 복원"을 누른 계정으로 구독을 이전. 한 번에 한 계정만 보유
- 근거: 결제 대행사들의 기본 동작과 같음. 한 번에 한 계정이라 돌려쓰기 이득이 없음
- 선반(소모성)은 이전하지 않음. 산 계정에만 귀속
- 서버 동작: 복원 요청 → 스토어 재조회 → 같은 원 거래 ID가 다른 계정에 있으면 소유자를 바꾸고 기록

### D9. 비로그인 구매 허용

- 결정: 로그인 없이 구매 가능. 구매는 기기 계정에 묶음. 결제 화면에서 로그인을 권유
- 근거
  - 애플 심사는 계정이 꼭 필요하지 않은 구매에 가입을 강제하면 반려한 사례가 있음 (지침 5.1.1 관련 포럼 다수)
  - 기기 계정이 이미 있어서 서버 쪽 귀속은 그대로 가능
- 감수하는 것: 로그인 없이 선반을 사고 기기를 잃으면 선반을 찾을 길이 없음
- 대응
  - 선반 구매 직전에 "로그인하면 기기를 바꿔도 유지됩니다" 안내
  - 구독은 스토어 복원으로 되찾을 수 있음 (D8)
  - 문의가 오면 주문 번호로 스토어에 조회해 수동 복구 (애플 `LookUpOrderID`)

### D10. 지급과 확인 순서

- 결정: 서버가 DB에 저장 → 구글 확인(acknowledge) → 앱이 `completePurchase`
- 근거
  - 확인을 먼저 하고 저장에 실패하면 돈만 받고 지급이 안 됨
  - 구글은 3일 안에 확인하지 않으면 자동 환불. 구독을 다시 시작한 경우도 새 구매라 다시 확인해야 함
  - Flutter `in_app_purchase` 공식 안내: `completePurchase`를 안 부르면 3일 뒤 환불. 지급 전에 부르면 누락
- 앱 쪽 규칙
  - 구매 스트림은 앱 시작 직후부터 듣기. 늦게 붙이면 거래를 놓침
  - 서버 검증이 성공한 뒤에만 `completePurchase`
  - 끝내지 못한 거래는 다음 실행 때 다시 제출
  - 구글의 결제 대기(pending) 상태에서는 지급하지 않음

### D11. 결제 실패 유예

- 결정
  - 유예 기간(grace period): 권한 유지
  - 유예가 끝난 뒤(애플 결제 재시도, 구글 계정 보류): 권한 해제
  - 애플 유예 기간은 App Store Connect에서 직접 켜야 함. 16일로 설정
  - 구글은 기본값 사용
- 근거
  - 애플은 기본이 꺼짐. 안 켜면 결제 실패 즉시 권한이 끊김
  - 구글 계정 보류는 기본으로 켜져 있고, 공식 안내가 "보류 중에는 차단"
  - 유예 기간을 기본값보다 줄이면 회복되는 구독이 줄 수 있다는 구글 안내
- 조사 자료 사이에 애플 결제 재시도 중 권한을 주는지에 대한 의견이 갈림. 유예 기간을 켜는 쪽으로 정리

### D12. 구독 해지·만료 시

- 결정: 유저가 만든 것은 아무것도 지우지 않음
  - 유료 벽지·선반 색: 기본값으로 표시. 고른 값은 저장해 두고 다시 구독하면 되돌림
  - 투명 선반 위젯: 기본 위젯으로 표시
  - 구독 전용 ASMR: 잠금
- 근거: 조사한 사례의 공통점이 "지우지 말고, 유료 기능만 막고, 다시 구독하면 원래대로"
- 해지(자동 갱신 끔)와 만료는 다름. 해지해도 만료일까지는 권한 유지

### D13. 환불된 선반

- 결정: 선반을 잠금. 꽂힌 책은 그대로 두고 그 선반에 새로 꽂기만 막음
- 근거: 책을 서랍으로 옮기거나 지우면 유저 기록이 바뀜. 환불 사유가 오결제일 수도 있음
- 다시 사면 잠금 해제
- 정환 확인: 잠긴 선반의 책을 다른 선반으로 옮기는 것은 허용하는 안

### D14. 무료 체험 없음

- 결정: 출시 때는 체험 없이 시작
- 근거
  - 조사 자료의 결론이 갈림. 체험이 유리한 분야와 아닌 분야가 다름
  - 무료 기능만으로 앱을 충분히 써 볼 수 있음. 유료는 꾸미기 중심
  - 체험을 넣으면 자격 확인, 체험 중 해지, 체험 악용 처리가 늘어남
- 나중에 스토어 설정만으로 추가 가능. 출시 후 전환율을 보고 다시 판단

### D15. 샌드박스 거래

- 결정: 운영 서버도 샌드박스 거래를 받아 지급. 환경을 기록하고 매출 집계에서 뺌
- 근거: 애플 심사와 TestFlight 구매는 샌드박스 거래인데 운영 서버로 들어옴. 거부하면 심사에서 결제가 실패함
- 구현: `NewStoreClientWithSandboxFallback` (ADR-0001)

### D16. 다른 스토어에서 이미 구독 중

- 결정
  - 권한은 계정 기준. 아이폰에서 구독하고 안드로이드에 로그인하면 `plus` 인정
  - 이미 `plus`가 있는 계정에는 결제 화면에서 구독 버튼 대신 "구독 중(다른 기기에서 결제)" 표시
- 근거: 양쪽에서 이중 결제되면 환불 문의로 이어짐
- 로그인 안 한 상태에서는 연결할 수 없음. D9의 로그인 권유로 보완

### D17. 개발 방식

- 결정
  - 결제 작업은 이슈 하나에 PR 하나. main에 바로 올리지 않음 (`AGENTS.md`)
  - 결제 화면은 빌드 플래그로 꺼 둔 채 머지. TestFlight 빌드에 노출되지 않게
  - 마이그레이션 번호는 머지 직전에 맞춤
- 근거: main 푸시마다 TestFlight가 돌고, DB 변경은 되돌리기 어려움

### D18. 서버 검증 전에는 지급하지 않음

- 문제: 결제는 됐는데 오프라인이거나 서버 검증이 실패한 경우, 앱이 먼저 열어 줄 것인가
- 결정: 열어 주지 않음. "구매 확인 중"으로 표시하고 자동으로 다시 제출
- 근거
  - 앱이 먼저 열면 위조 거래도 열림. 서버 재조회로 막는다는 ADR-0001의 전제가 무너짐
  - 거래를 끝내지 않고 남겨 두므로 구매는 사라지지 않음. 다음 실행 때 다시 제출됨 (D10)
- 감수하는 것: 서버 장애 중에는 결제한 유저가 기다려야 함
- 대응: 재시도 간격을 짧게, 화면에 "결제는 완료됐고 확인 중"임을 분명히 표시

### 해외 결제 확장 (D19~D23)

나중에 해외 결제를 붙일 계획이 있어, 지금 구조에서 미리 열어 둘 곳을 정함. "해외 결제"는 두 가지 뜻이 될 수 있어 둘 다 대비.

| 뜻 | 달라지는 것 | 대비 |
|---|---|---|
| 해외 스토어에서 판매 (다른 나라 App Store·Play) | 통화, 가격, 세금, 언어 | D20, D22, D23 |
| 스토어 밖 결제수단 (웹 결제, 해외 PG, 다른 앱 마켓) | 검증 방식, 알림 형식, 환불 주체 | D19, D21 |

### D19. 결제 경로를 값으로 둠

- 결정
  - 테이블의 "스토어" 칸을 "결제 경로"로 이름 붙이고 문자열 값으로 저장: `apple`, `google`. 나중에 `stripe`, `onestore` 같은 값이 추가됨
  - 코드는 결제 경로마다 같은 인터페이스를 구현: 거래 조회, 구독 상태 조회, 알림 해석, 확인(acknowledge)
  - 권한 계산은 결제 경로를 모름. 거래·구독 표만 봄
- 근거
  - 조사 자료의 공통점: 결제 경로는 "사건을 알려 주는 곳"일 뿐, 고객 상태의 기준은 그 위에 하나만 둠
  - 경로마다 능력이 다름. 애플은 환불 API가 없고, 구글과 Stripe는 있음. 애플은 요금제 변경을 알아서 처리하고, 구글과 Stripe는 개발자가 처리. 인터페이스에 "이 경로가 할 수 있는 것"을 따로 둠
- 지금 하지 않는 것: 애플·구글 외 경로의 구현. 자리만 열어 둠

### D20. 금액·통화·국가를 거래마다 저장

- 결정
  - 통화: ISO 4217 세 글자 (`KRW`, `USD`)
  - 금액: 정수. 통화 1단위 = 1000 (애플이 주는 형식 그대로). 실수형 금지
  - 판매 국가: 애플 `storefront`, 구글 `regionCode`
- 근거
  - 원화만 가정하고 금액 칸을 만들면 해외 판매 때 테이블을 고쳐야 함
  - 원화는 소수점이 없고 달러는 둘, 일부 통화는 셋. 정수 + 고정 배율이 안전
- 주의
  - 이 값은 참고용. 애플 공식 문서가 "거래의 가격·통화를 매출 정산에 쓰지 말 것, 정산은 App Store Connect 보고서 기준"이라고 명시
  - 구글 구매 조회 응답에는 금액·통화 칸이 없음 (구글 공식 Go 클라이언트 v0.299.0의 `SubscriptionPurchaseV2`, `ProductPurchaseV2` 타입으로 확인). 비워 둠. 필요하면 주문 조회 API로 따로 받음
  - 환율 환산은 서버에서 하지 않음

### D21. 상품 목록을 서버 표로

- 결정: "어떤 상품 ID가 어떤 권한(또는 선반 몇 칸)을 주는가"를 코드가 아니라 표에 둠
- 근거: 나라별 상품, 새 요금제, 새 결제 경로가 생겨도 줄 추가로 끝남
- 상품 ID에 통화나 나라를 넣지 않음. 스토어는 상품 하나에 나라별 가격을 붙이는 구조

### D22. 가격은 스토어가 주는 값을 표시

- 결정: 앱 코드와 문구에 "2,500원" 같은 숫자를 적지 않음. 스토어에서 받은 현지 가격 문자열을 그대로 표시
- 근거
  - 같은 상품이 나라마다 통화와 금액이 다름
  - 스토어 가격을 바꿔도 앱을 다시 배포하지 않아도 됨
  - 화면의 가격과 실제 결제 금액이 다르면 심사 반려 사유
- 할인율 문구("34% 할인")도 받은 가격으로 계산

### D23. 시각은 UTC

- 결정: 구매·만료·유예 시각을 UTC로 저장. 만료 여부는 서버 시계로 판단. 화면 표시만 기기 시간대
- 근거: 해외 유저가 생기면 시간대가 섞임. 기기 시계는 유저가 바꿀 수 있음

### 해외 판매 때 따로 챙길 것 (지금은 기록만)

- 세금: 스토어가 대부분 나라에서 판매자로서 현지 세금을 처리한다는 2차 자료가 있음. 한국 개발자의 신고 범위는 세무사 확인 필요
- 지역별 규정: 미국, EU 등은 스토어 밖 결제 안내가 허용되는 범위가 다름. 붙일 때 그 시점 규정 확인
- 언어: 결제 화면 문구, 약관, 개인정보 처리방침
- 가격: 나라마다 따로 정할지, 스토어의 자동 환산을 쓸지. 조사 자료는 "숫자만 바꿔서는 전환이 안 오른다"고 지적

## 4. 감수하는 것

- 선반은 스토어 복원이 안 됨. 계정이 유일한 기록 (D1, D9)
- 구독 이전을 허용해 Apple ID 하나를 여러 앱 계정이 번갈아 쓸 수 있음. 동시에는 한 계정 (D8)
- 하루 1회 대조 작업이 필요함. 서버에 정기 실행 수단이 있어야 함 (D4)
- 샌드박스 거래가 운영 DB에 섞임 (D15)
- 지금은 안 쓰는 칸(통화, 판매 국가, 상품 표)을 미리 만듦. 대신 해외 결제 때 테이블을 안 고침 (D19~D21)

## 5. 다시 검토할 조건

- 애플 심사가 소모성 선반을 반려 → D1을 A(비소모성)로
- 선반 분실 문의가 반복 → D9를 "선반은 로그인 필수"로
- 구독 돌려쓰기가 눈에 띔 → D8을 "첫 계정 고정 + 문의로 이전"으로
- 출시 후 구독 전환율이 낮음 → D14 무료 체험 도입

## 6. 정환 확인이 필요한 것

- D1: "최대 3칸"의 범위 (연도 책장마다 / 계정 전체)
- D12: 유료 꾸미기를 기본값으로 되돌리는 방식에 동의하는지
- D13: 잠긴 선반의 책 이동 허용 여부
- D14: 무료 체험 없이 출시하는 것
- 가격: 결제 계획 보고 참고

## 부록 B. 확인 못 한 것

- 2026-11-19 조사로 늘어난 항목은 [조사 종합 9장](../reports/2026-11-19-iap-pitfalls.md)과 이슈 #41에 있음
- 애플 거래 내역 조회가 끝난 소모성 거래도 돌려주는지. 돌려준다면 선반도 서버에서 복원 가능해 D1·D9의 약점이 줄어듦
- 구글 계정 하나에 앱 계정이 여럿일 때의 동작. 자료를 찾지 못함

- 서버(KoDeploy)에서 정기 작업을 돌릴 수 있는지
- 한국어권 사례. 이번 조사는 영어·중국어 자료 중심
- "해외 결제"가 해외 스토어 판매인지 스토어 밖 결제수단인지. 둘 다 대비했지만 범위는 정환과 확인 필요
- 구글 주문 조회 API로 금액·통화를 받을 수 있는지 (구매 조회 응답에는 없음을 타입 정의로 확인)
- 한국 개발자가 해외 판매분에 대해 신고할 세금 범위
