# ADR-0002: 인앱결제 설계 결정 (상품 유형, 장부, 계정 연결, 실패 처리, 해외 확장)

- 상태: 제안 (정환 확인 후 "승인"으로 변경)
- 날짜: 2026-11-18 (D1 범위·D9 2026-11-19 갱신)
- 결정자: 범수, 정환
- 앞선 결정: [ADR-0001](0001-iap-server-go.md) (Go 서버, `go-iap`, 스토어 재조회)
- 이어지는 결정: [ADR-0003](0003-iap-compliance.md) (법규 대응: 고지, 동의, 해지, 기록)
- 가격은 이 문서에서 다루지 않음. 결제 계획 보고(팀 안에서만 공유)에 있음

## 1. 배경

- ADR-0001은 "어디에, 무엇으로 만드는가"만 정했음
- 구현을 시작하려면 상품 유형, 테이블, 계정 연결, 실패 처리 방식이 먼저 정해져야 함
- 2026-11-18에 영어권·중국어권 자료를 조사해 갈림길마다 하나씩 고름
- 자료 대부분은 결제 대행사 문서, 개발자 포럼, 개인 블로그. 공식 문서로 확인한 것과 아닌 것을 부록 A에 구분

## 3. 결정과 근거

### D1. 추가 선반: 연도 책장마다, 소모성 상품

- 범위 (2026-11-19 정환 확정)
  - 연도 책장마다 따로 삼. 2026년 책장에서 산 칸은 2027년 책장에 열리지 않음
  - 책장 한 개는 6칸. 3칸까지 무료, 나머지 3칸은 돈을 내고 엶
  - 상품 2개: 1칸, 3칸 묶음(1칸 세 번보다 쌈). 가격은 결제 계획 보고에만 적음
  - 지금 코드는 책장 5칸(무료 3 + 유료 2)이라 6칸으로 바꿔야 함 (`app/lib/features/home/locked_rows.dart`의 `shelfSlots`, 홈 3D 책장)

- 선택지
  - A. 비소모성: 스토어가 복원해 줌. 계정당 한 번만 구매 가능
  - B. 소모성: 여러 번 구매 가능. 스토어 복원 없음
  - C. 기간제: 1년 뒤 만료
- 결정: B
- 근거
  - 선반은 1칸, 3칸으로 팔고 여러 번 살 수 있어야 함. 비소모성은 같은 상품을 두 번 못 삼
  - A로 하려면 "연도 × 칸 번호"마다 상품을 따로 등록해야 함. 해마다 등록·심사가 반복됨
  - C는 지난 해 책장의 선반이 사라져 "해마다 기록" 컨셉과 어긋남. 구글에는 기간제 유형이 없어 서버에서 흉내 내야 함
- 감수하는 것
  - 스토어의 "구매 복원"으로는 선반이 돌아오지 않음. 서버 계정이 유일한 기록
  - 애플 심사에서 "영구 상품은 비소모성이어야 한다"는 지적이 나온 사례가 있음. 반대로 소모성으로 바꿔 통과한 사례도 있음. 결과가 갈림
- 대응
  - 선반 구매 기록은 계정에 묶어 서버에 보관. 로그인하면 어느 기기에서든 복원
  - 심사 메모에 "선반은 계정에 기록되고 로그인으로 복원된다"고 적음
  - 반려되면 심사 메모로 연도 책장 구조(해마다 새 책장, 같은 상품을 여러 번 삼)를 설명하고 다시 냄. A로 바꾸려면 "연도 × 칸"마다 상품을 해마다 등록해야 해 마지막 수단
- 연도 책장마다라 칸마다 비소모성 상품을 따로 두는 대안(조사 종합 8-2 T6, 이슈 #27에서 논의)은 쓸 수 없음. 해마다 사는 횟수에 끝이 없어 소모성으로 확정
- 로그인이 필수(D9)라 서버 계정 기록이 늘 남음. "비로그인으로 산 뒤 앱을 지우면 되찾을 길이 없다"는 약점은 없어짐
- 구현 규칙 (2026-11-19, 서버 PR #21~#48·앱 PR #45에 구현)
  - 개정 (2026-11-27, #53·#55): 아래 규칙 가운데 연도를 찾는 길은 D7 개정(결제 의도 `POST /iap/intent`)으로 바뀜. 계정 연결 값은 계정마다 하나. 오류 코드는 결제 키트 이름으로: `iap_shelf_full` → `iap_cap_full`, `iap_shelf_busy` → `iap_target_busy`, `iap_shelf_year_missing` → `iap_target_missing`, `shelfNoYear` → `noTarget`. 칸 수 규칙(최대 3, 묶음, 5분 예약)은 그대로이고 키트 `Rules.Cap`·`Hold`로 둔다
  - 어느 연도 책장의 칸인지 거래마다 기록. 스토어 거래에는 연도가 없으므로, 선반을 살 때 스토어에 넘기는 계정 연결 값(D7)을 "계정 × 연도"마다 따로 발급해 서버가 그 값으로 연도를 찾음. 앱이 결제 중 꺼져도, 스토어 알림으로 와도 연도를 잃지 않음
  - 칸 수 = 그 연도 책장에서 환불 안 된 선반 거래의 칸 합. 최대 3
  - 3칸 묶음은 그 연도에 산 칸이 없을 때만 팖. 1칸은 남은 칸이 있을 때만
  - 그 해 3칸을 다 열었으면 연도별 계정 연결 값을 줄 때 409 `iap_shelf_full`로 막아 결제창을 띄우지 않음
  - 결제 중 예약 (2026-11-19 범수 결정): 계정 연결 값을 줄 때 요청한 칸을 5분 동안 잡아 둠. 산 칸 + 예약 칸 + 요청 칸이 3을 넘으면 409 `iap_shelf_busy`(다른 기기에서 결제 중). 결제를 취소·실패하면 앱이 바로 풀고, 제출되면 서버가 품. 태블릿과 휴대폰에서 함께 사는 경우를 막음
  - 연도를 끝내 모르는 거래(앱 밖 구매 등)는 기록만 하고 칸은 주지 않음(422 `iap_shelf_year_missing`). 같은 거래를 연도와 함께 다시 내면 그때 칸을 줌. `/admin/iap/stats`의 `shelfNoYear`로 셈
    - 연도를 모르는 동안은 소비하지 않고, 앱도 거래를 끝내지 않음(2026-11-26 코드 리뷰). 소비한 뒤 돌려보내면 앱이 거래를 끝내 돈만 받은 상태가 됨. 끝내 연도를 못 받으면 구글은 3일 뒤 자동 환불
    - 2일이 지나도 연도를 모르면 정기 대조가 `orders.refund`(revoke=true)로 환불(2026-11-26 범수 결정). 구글 권고가 "자동 환불에 맡기지 말고 직접 환불"이라서. 3일 자동 환불은 안전망으로만 남음. 환불 고지(T9)에는 `opened=false`를 붙여 "선반이 잠겼다" 대신 "열지 않고 환불했다"고 씀
  - 예약 번호는 그 예약보다 뒤에 끝난 결제에만 씀(1분 여유). 앱이 지금 결제의 예약 번호를 붙여 전에 끝내지 못한 옛 거래를 내도, 옛 거래는 계정 연결 값의 연도로 가고 예약은 그대로 남음(2026-11-26)
  - 그래도 3칸을 넘으면(예약이 만료된 느린 결제 등) 3칸까지만 인정하고 넘은 거래는 자동 환불 (2026-11-19 범수 결정). 구글은 서버가 `orders.refund`로 환불, 애플은 개발자 환불 API가 없어 고지로 환불 요청 방법을 안내(고지 문구 T15)
  - 환불하면 그 연도 책장의 칸만 닫음(D13). 다른 연도 책장은 그대로

- 재검토 결과 (2026-11-19): 비소모성 여러 개로 바꾸는 안은 선반이 연도 책장마다로 정해져 쓸 수 없음. 소모성 유지. 구글은 소비한 구매를 스토어에서 다시 조회할 수 없지만, 로그인이 필수(D9)라 서버 계정 기록으로 되찾음. 근거: [조사 종합 8-2 T6](../reports/2026-11-19-iap-pitfalls.md)

### D2. 구독은 권한 하나

- 결정: 권한 이름 `plus` 하나. 월·연 상품 모두 같은 권한을 줌
- 애플: 구독 그룹 1개에 월·연 상품. 구글: 구독 1개에 기본 요금제 2개
- 근거: 같은 그룹 안에서는 월↔연 전환을 스토어가 처리함. 서버는 "권한이 있는가"만 판단

### D3. 권한의 기준은 서버 DB

- 결정: 서버가 "이 계정에 `plus`가 있는가, 선반이 몇 칸인가"를 가짐. 앱은 받아서 캐시
- 근거
  - 앱에만 두면 기기 변경, 환불, 다른 플랫폼 로그인을 처리할 수 없음
  - 조사한 자료 대부분이 같은 구조를 권함: 서버가 기준, 앱은 임시 상태
- 앱 동작: 실행할 때와 결제 직후에 서버에서 권한을 받아 옴. 오프라인이면 마지막 캐시 사용

### D4. 권한 갱신 경로는 세 가지

- 결정
  1. 앱이 결제 직후 거래를 서버에 제출
  2. 스토어 알림(애플 V2, 구글 RTDN) 수신
  3. 정기 대조: 서버 안 작업이 1분마다 돎. 단계별 주기는 아래(2026-11-27 코드 기준, `server/iapkit/notify.go`·`store.go`)
     - 스토어 확인 못 마친 거래: 매 바퀴(4일 안)
     - 실패한 알림 재처리: 1분부터 2배씩, 8일까지
     - 칸을 주지 않은 선반의 환불: 2분부터 2배씩 6시간까지, 20번
     - 만료가 다가온 구독 재조회: 만료 5분 전부터 10분마다. 끝난 구독은 60일 동안 하루 한 번
     - 빠진 알림·환불 메우기(애플 알림 이력, 구글 무효 구매 목록): 6시간마다
   - 한 바퀴는 2분 기준. 단계마다 마감 시각(시작부터 30·60·80·95·115초)을 두고, 마감이 지난 건은 다음 바퀴로 넘김(2026-11-27, #23)
     - 마감은 새 일을 시작하지 않게만 함. 이미 시작한 환불 요청·스토어 확인과 그 기록은 끝까지 함(최대 15초 넘김). 끊으면 스토어와 원장이 어긋남
     - 빠진 알림 메우기가 마감에 끊기면 6시간이 아니라 15분 뒤 다시
     - 근거: 마감이 하나뿐이면 느린 스토어 하나가 확인 단계에서 2분을 다 써 구독 재조회·갱신 고지가 돌지 못함
     - 마감은 누적이라 앞 단계가 빨리 끝나면 뒤 단계가 그 시간을 씀. 기한이 있는 구글 3일 확인에 가장 많이 줌
     - 마감에 끊긴 알림은 실패로 세지 않음(8일 시도 횟수를 쓰지 않음)
   - 스토어가 한도 초과(429)로 답하면 그 경로는 `Retry-After`까지 부르지 않음. 모르면 1분, 길어도 1시간(2026-11-27, #23)
     - 근거: 애플 한도는 시간 단위라 1분마다 다시 부르면 늦게 풀림
     - 쉬는 동안 건너뛴 건과 처리 도중 한도에 걸린 건은 시도 횟수(환불 20번, 알림 8일)를 쓰지 않음
     - 구글은 403에 한도 사유(`rateLimitExceeded`, `userRateLimitExceeded`, `quotaExceeded`)가 붙은 것도 한도로 봄
     - 남은 약점: 알림·구독 목록은 경로로 거르지 않고 오래된 순으로 뽑음. 쉬는 경로의 건이 100건(구독 200건)을 넘으면 그동안(최대 1시간) 다른 경로의 건이 밀림
     - 제출 요청은 쉬는 중이면 503 `iap_store_unavailable`. 앱은 거래를 끝내지 않고 다시 냄
- 세 경로 모두 받은 내용을 믿지 않고 스토어 재조회 후 반영 (ADR-0001)
- 근거
  - 1만 있으면 유저가 앱을 다시 안 열 때 갱신·환불을 모름
  - 2만 있으면 알림을 놓쳤을 때 복구가 안 됨. 애플은 실패한 알림을 며칠간 몇 번만 다시 보냄
  - 중국어권 자료가 "알림은 보조, 주기적 조회가 있어야 누락(掉单)을 메운다"고 반복해서 지적
- 구글 알림은 "상태가 바뀌었다"만 알려 줌. 최종 상태는 API로 조회해야 함 (공식 문서)
- 구글 알림은 도착 순서가 보장되지 않음. 알림의 사건 시각으로 최신 여부를 판단하거나, 순서와 무관하게 재조회 결과로 덮어씀 (국내 구현 사례)

### D5. 테이블 4개 (구현하면서 8개로 늘어남)

- 지금 테이블 8개와 칸마다의 이유는 [`spec/erd.md`](../spec/erd.md). 아래는 처음 결정한 4개의 기록
- 늘어난 테이블: 계정 연결 값(D7, 유저 하나가 값을 여러 개 가져서), 선반 결제 중 예약(D1), 결제 고지(ADR-0003 L11), 요금제 주기(연 구독 갱신 예정 고지)


| 테이블 | 한 줄의 단위 | 주요 열 |
|---|---|---|
| 거래 | 거래 1건 | 결제 경로, 거래 ID, 원 거래 ID, 상품 ID, 사용자, 환경, 상태, 구매 시각, 통화, 금액, 판매 국가 |
| 구독 | 구독 1건(첫 결제부터 자동 갱신이 이어지는 동안) | 결제 경로, 원 거래 ID(구글은 구매 토큰), 사용자, 상품 ID, 만료 시각, 상태, 자동 갱신 여부, 유예 종료 시각 |
| 알림 기록 | 받은 알림 1건 | 결제 경로, 알림 ID, 종류, 원문, 처리 결과, 받은 시각 |
| 상품 | 파는 상품 1개 | 결제 경로, 상품 ID, 종류(구독·선반), 주는 권한 또는 칸 수 |

- 권한은 따로 저장하지 않고 위 테이블에서 계산
  - `plus`: 구독 테이블에 유효한 줄이 있는가
  - 선반 칸 수: 거래 테이블에서 환불 안 된 선반 거래의 합
- 근거: 권한을 따로 저장하면 원장과 어긋날 수 있음. 규모가 작아 계산 비용은 문제가 안 됨
- 알림 원문을 남기는 이유: 분쟁과 버그 추적

### D6. 중복 방지 키

- 거래: (스토어, 거래 ID) 유일
- 구독: (스토어, 원 거래 ID) 유일. 갱신마다 거래 ID는 새로 생기므로 같은 구독 1건은 원 거래 ID로 묶음
- 알림: (스토어, 알림 ID) 유일. 같은 알림이 다시 와도 한 번만 처리
- 구글: 구독을 다시 시작하거나 요금제를 바꾸면 구매 토큰이 새로 나옴. 이전 토큰(`linkedPurchaseToken`)을 따라가 옛 구독을 끝내고 새 구독으로 주인을 넘김

### D7. 계정 연결 값

- 문제: 애플 `appAccountToken`은 UUID만 받음. 우리 사용자 ID는 정수(BIGINT)
- 결정: 사용자마다 결제용 UUID 1개를 발급해 저장. 애플에는 그 UUID, 구글 `obfuscatedAccountId`에도 같은 값
- 근거
  - 구글은 이 값에 이메일 같은 개인정보를 넣으면 구매를 막음 (공식 문서). 무작위 UUID라 해당 없음
  - 사용자 ID를 그대로 넘기지 않아 내부 번호가 노출되지 않음
- 검증: 스토어 조회 결과의 값이 요청한 계정의 UUID와 다르면 지급 거부
- 개정 (2026-11-27): 한 번 사는 상품에도 이 값 하나를 쓴다
  - 그동안: 추가 선반은 연도 책장마다 값을 따로 주고, 돌아온 값으로 연도를 찾았다(2026-11-19, #6)
  - 바꾼 까닭
    - 애플은 한 계정의 모든 구매에 같은 값을 쓰라고 권한다 ([WWDC25 세션 249](https://developer.apple.com/videos/play/wwdc2025/249/))
    - 구매마다 새 값을 넣었는데 첫 값이 돌아왔다는 보고가 있다. 애플 답은 "Feedback을 내라"뿐이고 풀리지 않았다 ([포럼 800411](https://developer.apple.com/forums/thread/800411))
    - 구글은 이 값을 구매자의 앱 계정으로 보고, 한 계정이 여러 기기에서 짧은 시간에 사는 것을 잡는 데 쓴다 ([Fight fraud and abuse](https://developer.android.com/google/play/billing/security))
    - 구매에 임의의 정보를 실어 알림까지 보내는 공식 통로는 두 스토어 모두 없다(구글 developer payload 폐지)
  - 대신: 어느 해 책장인지는 서버에 남긴 결제 의도로 찾는다(`POST /iap/intent`, `iap_reservations.keep_until`). 앱이 붙인 번호가 먼저, 없으면 결제 전 72시간 안의 의도가 한 대상으로 모일 때만 그 대상(갈리면 추측하지 않고 앱 제출을 기다림. 리뷰 반영 2026-11-27)
  - 감수하는 것: 의도 보관 시간(8일: 애플 알림 재전송 약 6.5일, 구글 Pub/Sub 보관 7일보다 길게)이 지나 끝난 결제는 대상을 모른다. 앱이 연도와 함께 다시 내지 않으면 2일 뒤 환불(D1의 기존 길)

### D8. 스토어 계정 하나, 앱 계정 여럿

- 문제
  - 애플은 Apple ID 하나에 구독 그룹당 구독 하나만 허용
  - `appAccountToken`이 첫 구매 때 굳는지는 불확실. 포럼 관측이 엇갈리고(2023: 처음 값 유지, 2026: 교차 변경 때 바뀜) 애플 문서에는 그런 문장이 없음
  - 2025-06에 값을 나중에 넣거나 바꾸는 API(Set App Account Token)가 생김. 구독을 옮길 때 쓸지는 이슈 #29에서 결정
  - 같은 Apple ID·구글 계정으로 다른 로그인 계정에 들어갈 수 있음. "첫 계정에만 귀속"으로 하면 계정을 바꾼 유저가 잠김
- 결정: "구매 복원"을 누른 계정으로 구독을 이전. 한 번에 한 계정만 보유
- 근거: 결제 대행사들의 기본 동작과 같음. 한 번에 한 계정이라 돌려쓰기 이득이 없음
- 선반(소모성)은 이전하지 않음. 산 계정에만 귀속
  - 결제한 뒤 제출하기 전에 계정을 바꿔 다른 계정이 그 거래를 내면, 계정 연결 값으로 결제한 계정을 찾아 그 계정에 칸을 주고 소비함. 낸 계정에는 409 `iap_other_account`(앱이 거래를 끝냄). 전에는 409만 줘서 애플에서 결제한 사람이 돈만 내고 칸을 잃을 수 있었음(2026-11-26 코드 리뷰)
  - 결제한 계정이 제출 전에 탈퇴했으면(계정 연결 값 줄이 함께 지워짐) 낸 계정에 주지 않음(2026-11-26 범수 결정). 주인 없이(`user_id NULL`) 원장에 남기고 소비하지 않음. 구글은 서버가 바로 환불(revoke=true), 실패하면 정기 대조가 다시 함. 애플은 409 `iap_owner_gone` 문구로 App Store 환불 요청을 안내
    - 조사: 결제 대행사 기본값은 "지금 낸 계정에 지급". 로그인 필수 앱에는 "원래 계정 유지"가 권장되고, 한 번 사는 상품은 옮기지 않는다는 이 절의 원칙과도 맞아 거절을 고름
    - 계정 연결 값이 UUID 모양이 아니면 우리가 발급한 값이 아니므로 탈퇴로 보지 않고 409 `iap_other_account`
- 서버 동작: 복원 요청 → 스토어 재조회 → 같은 원 거래 ID가 다른 계정에 있으면 소유자를 바꾸고 기록

### D9. 로그인 필수

- 결정 (2026-11-19 정환): 오프라인(기기) 계정을 허용하지 않음. 앱을 시작할 때 로그인부터 함. 구매와 기록은 로그인 계정 기준으로 전부 동기화
- 처음 결정(2026-11-18)은 "비로그인 구매 허용, 기기 계정에 묶고 로그인 권유"였음. 이 결정으로 뒤집음
- 근거
  - 기록을 계정에 보관하는 것이 서비스의 중심이라 로그인 없는 사용을 두지 않음
  - 구매가 늘 로그인 계정에 묶여 "기기 계정으로 산 뒤 로그인하면 구매가 어디에 남는가"(이슈 #30) 문제가 생기지 않음
  - 선반(소모성)을 서버 기록으로만 되찾는 약점(D1)이 사라짐
- 감수하는 것
  - 애플 지침 5.1.1(v): 계정 기반 기능이 크지 않은 앱은 로그인 없이 쓰게 하라고 함. 우리는 계정 동기화가 핵심 기능이라는 점을 심사 메모에 적음. 반려되면 다시 검토
- 할 일 (로그인 작업은 정환)
  - 앱 시작 화면에 로그인
  - 기존 기기 계정 사용자를 로그인 계정으로 옮기는 방법 (지금 서버의 계정 전환은 데이터를 합치지 않음, `recordSwitch`)
  - 결제 화면은 로그인한 계정에서만 열림

### D10. 지급과 확인 순서

- 결정: 서버가 DB에 저장 → 구글 확인(acknowledge) → 앱이 `completePurchase`
- 근거
  - 확인을 먼저 하고 저장에 실패하면 돈만 받고 지급이 안 됨
  - 구글은 3일 안에 확인하지 않으면 자동 환불. 구독을 다시 시작한 경우도 새 구매라 다시 확인해야 함
  - Flutter `in_app_purchase` 공식 안내: `completePurchase`를 안 부르면 3일 뒤 환불. 지급 전에 부르면 누락
- 앱 쪽 규칙
  - 구매 스트림은 앱 시작 직후부터 듣기. 늦게 붙이면 거래를 놓침
  - 서버 검증이 성공한 뒤에만 `completePurchase`
  - 끝내지 못한 거래는 다음 실행 때 다시 제출
  - 안드로이드는 끝나지 않은 구매가 구매 스트림으로 다시 오지 않음(앱이 떠 있을 때만 옴). 앱을 켤 때 `queryPastPurchases`로 서버가 아직 확인하지 않은 구매를 물어 다시 냄. 복원(`restore`)으로 내지 않아 다른 계정의 구독을 옮기지 않음(2026-11-26)
- 서버 쪽 규칙 (2026-11-26 코드 리뷰)
  - 커밋 뒤 확인·환불 요청은 요청과 떼어 낸 컨텍스트(`context.WithoutCancel`)에 15초를 새로 줌. 앞의 스토어 조회가 시간을 다 썼거나 사용자가 앱을 닫아도 끝까지 함. 알림 처리도 같음
  - 결제 트랜잭션에는 `lock_timeout` 5초, `statement_timeout` 10초(`set_config(..., true)`라 그 트랜잭션에만). 넘으면 요청은 503 `iap_busy`, 대조는 다음 바퀴(2026-11-27, #23)
    - 근거: 같은 대상을 잡은 트랜잭션이 멈추면 뒤 요청이 잠금을 기다리며 연결 풀을 다 잡음. 키트를 붙인 앱의 다른 쿼리까지 멈춤
    - `idle_in_transaction_session_timeout` 30초도 같은 방식으로 걸음. 트랜잭션을 연 채 멈춘 연결을 PostgreSQL이 끊어 잠금을 풂. 운영 DB 역할 설정 대신 코드에 둠. 교착(40P01)도 503 `iap_busy`(2026-11-28)
  - 상한 개수를 바꾸는 쓰기는 모두 유저 줄 잠금(`iapLockUser`)을 먼저 잡은 트랜잭션 안에서 함: 제출, 상한 판정, 환불 회수, 애플 환불 되돌림(2026-11-28)
    - 근거: READ COMMITTED에서 잠금으로 순서를 세우는 설계는 모든 쓰기가 같은 잠금을 잡을 때만 맞음. 회수·되돌림이 잠금 밖이었음(트랜잭션 설계 조사, 우아한형제들 WMS 취소 경로 사례)
    - 되돌림 뒤 상한을 다시 판정함. 환불된 동안 같은 대상을 또 샀으면 되돌린 거래가 넘은 거래(`over_cap`)가 되고 넘김 고지(T15)를 씀. 애플은 서버가 환불할 수 없어 사용자에게 애플 환불 요청을 안내함
    - 잠금은 `FOR NO KEY UPDATE`. 결제끼리는 막고, 유저를 FK로 가리키는 다른 테이블의 쓰기(`FOR KEY SHARE`)는 막지 않음
  - 대조의 확인 재시도가 실패하면 스토어를 다시 조회함. 이미 확인(소비)된 구매면 확인을 마친 것으로 적음. 구글은 이미 소비한 구매에 다시 요청하면 400 `invalidPurchaseState`(2026-11-28)
  - 스토어 설정은 스토어마다 따로 검사함. 한쪽이 틀려도 다른 쪽은 켜고, 틀린 것은 경보(`configProblems`)로 올림(2026-11-28 리뷰)
    - 근거: 전체를 끄면 구글 키 실수 하나로 애플 결제 제출까지 404가 됨. 서버 시작을 막는 방식은 결제 설정 실수로 독서 앱 전체가 내려가서 고르지 않음
  - 실패한 알림은 30일까지 다시 시도함(전에는 8일). 유효·환불 구독도 만료 전이면 하루에 한 번 스토어에 다시 물음(2026-11-28 리뷰)
    - 근거: 키·권한 문제가 8일을 넘기면 환불이 영영 반영되지 않았고, 환불된 연 구독이 만료일까지 유효로 남을 수 있었음
  - 알림 경로도 수량 구매(2개 이상)를 받지 않음. 제출 경로와 같음(2026-11-28 리뷰)
  - 구글 구독 갱신 거래의 구매일은 그 회차 주문(`orders.get`)의 `createTime`. 구독 조회에는 처음 구독한 날만 있음. 주문 조회가 실패하면 시작일이 남음(2026-11-28 리뷰)
  - 같은 권한의 다른 구독이 유효하면 한 구독이 끝나도 만료 고지(T8)를 쓰지 않음. 구글 요금제 교체로 옛 구독이 끝나는 경우(2026-11-28 리뷰)
