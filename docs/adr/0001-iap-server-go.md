# ADR-0001: 인앱결제 서버 검증을 기존 Go 서버에서 go-iap으로 구현

- 상태: 제안 (정환 확인 후 "승인"으로 변경)
- 날짜: 2026-11-18
- 결정자: 범수, 정환
- 관련 문서: [ADR-0002 설계 결정](0002-iap-design.md), 결제 계획 보고(상품·가격, 저장소에 올리지 않고 팀 안에서만 공유)

## 1. 배경

- 책장 한켠에 유료 상품(구독, 추가 선반) 도입. iOS·안드로이드 모두 대상
- 디지털 상품이라 스토어 인앱결제 사용. PG는 안 붙임
- 서버 검증 필요
  - 앱이 보낸 구매 성공 응답만 믿으면 위조, 영수증 재사용, 계정 간 공유에 뚫림
- 스토어 서버 알림 수신 필요
  - 구독의 갱신, 해지, 결제 실패, 환불은 앱이 꺼져 있을 때 일어남
- 현재 서버: Go 1.27 + pgx + PostgreSQL, KoDeploy 배포, 마이그레이션 V18까지
- 애플 공식 서버 라이브러리: Swift, Java, Python, Node만 있음. Go 없음

## 2. 결정

1. 결제 검증과 구매 기록을 기존 Go 서버(`server/`)에 구현. 별도 서버 없음
2. 애플: `github.com/awa/go-iap` v1.59.1 이상
3. 구글: 같은 라이브러리의 `playstore` 패키지. 내부는 구글 공식 `androidpublisher` 클라이언트
4. 지급 판단은 서명 검증이 아니라 스토어 API 재조회 결과로 함
   - 앱이 거래를 올리면 서버가 거래 ID(구글은 구매 토큰)로 스토어에 직접 조회
   - 서버 알림을 받아도 같은 방식으로 다시 조회한 뒤 상태 변경
5. 조회 결과의 번들 ID(패키지 이름), 상품 ID, 환경을 우리 값과 비교
6. 거래 ID에 유일 제약. 같은 구매는 한 번만 지급
7. 구매는 서버 계정에 묶음. 구매할 때 계정 식별자를 함께 넘김
   - 애플 `appAccountToken`, 구글 `obfuscatedAccountId`
8. 스토어 라이브러리 호출은 인터페이스 하나 뒤에 둠. 나중에 라이브러리 교체나 검증 분리가 가능하도록
9. 서명 검증은 직접 구현하지 않고 라이브러리에 맡김. 우리가 짜는 것은 재조회, 값 비교, 중복 방지, 계정 확인
10. 알림 수신 주소 보호
    - 서명 검증을 통과한 알림만 스토어에 재조회 (도배로 API 할당량이 소진되지 않도록)
    - 구글 Pub/Sub 푸시는 인증 토큰 확인
    - 호출 횟수 제한
      - 개정 (2026-11-27): 제한은 구매 제출에만 둔다(사용자당 1분 30번). 알림 주소는 본문 1MB 제한과 서명·인증 확인이 저장보다 앞이라, 위조 요청은 DB와 스토어 API에 닿지 않는다. 스토어의 정상 재전송을 제한이 막으면 알림을 잃을 수 있어 두지 않는다(이슈 #11)
11. 스토어 키는 결제에 필요한 최소 권한만
    - 애플: 인앱결제 키만 사용. App Store Connect 팀 키는 서버에 넣지 않음
    - 구글: 서비스 계정에 앱 하나, 주문·구독 관련 권한만. 출시·계정 관리 권한 없음

## 3. 검토한 대안

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. 서버 전체를 Java(Spring)로 | 애플·구글 공식 라이브러리 모두 있음. 한국어 예제 가장 많음 | 서버 재작성. 유휴 메모리 수백 MB로 증가 | 기각 |
| B. 서버 전체를 Rust로 | 메모리 최소. 가비지 컬렉터 멈춤 없음 | 애플 공식 라이브러리 없는 것은 Go와 같음. 개발 속도 저하 | 기각 |
| C. 애플 검증만 Java·Node 서버로 분리 | 애플 공식 라이브러리의 서명 검증 사용 | 서버 2개. 배포·모니터링 2벌. 검증 서버가 죽으면 지급 중단. 서버 간 통신 인증이 새 약점 | 기각 |
| D. 라이브러리 없이 직접 구현 | 외부 의존성 없음 | JWT 발급, 인증서 체인 검증을 우리가 관리 | 보류 |
| E. RevenueCat 같은 대행 서비스 | 검증, 알림, 구독 상태 관리를 대신 해 줌 | 매출이 늘면 수수료. 구매 기록이 외부에 있음. 비용 미조사 | 보류 |

- B 보충: 우리 서버는 DB와 스토어 응답을 기다리는 시간이 대부분이라 Rust의 성능 이득이 안 드러남
- C 보충: 결정 4번(재조회)으로 같은 목적을 더 싸게 달성
- D 보충: `go-iap`이 관리되지 않게 되면 다시 검토

## 4. 근거

- 자세한 내용: 부록 A(언어 비교), 부록 B(기업 사례), 부록 C(라이브러리 검토)
- 인앱결제 서버가 하는 일은 스토어 조회, 알림 수신, DB 기록
- 정확성은 PostgreSQL의 트랜잭션과 유일 제약에서 나옴. 언어와 무관
- 결제에 Go를 쓰는 사례 있음: American Express(카드 결제망), PayPal(결제 플랫폼 일부), MercadoLibre
- `go-iap`은 2014년부터 관리됨. 2026년 릴리스 12개 이상
- 다른 언어로 얻는 것은 애플 공식 라이브러리 하나. 잃는 것은 서버 재작성 또는 서버 2개 운영

## 5. 결과

### 좋아지는 것

- 서버, 배포, DB가 하나로 유지됨
- 메모리 부담이 늘지 않음
- 재조회 구조라 라이브러리의 서명 검증에 구멍이 나도 지급이 안 뚫림

### 감수하는 것

- 애플 쪽은 커뮤니티 라이브러리에 의존
  - 2026-11-10 서명 위조 취약점(#348) 발생, v1.59.1에서 수정
- 이 저장소는 보안 권고를 따로 안 냄. 릴리스 알림을 직접 챙겨야 함
- 구매마다 스토어 API 호출 1회 추가. 스토어 API가 느리거나 죽으면 지급 지연
- `server/go.mod`에 `google.golang.org/api`, gRPC 등 간접 의존성 증가
- `x/oauth2`, `x/crypto` 버전 상승. 소셜 로그인 테스트 재실행 필요
- 인증서 폐기 확인(OCSP) 안 함

## 부록 A. Java, Go, Rust 비교

| 항목 | Go | Java(Spring) | Rust |
|---|---|---|---|
| 유휴 메모리 | 수십 MB | 수백 MB | 수 MB~수십 MB |
| 시작 직후 속도 | 즉시 최고 속도 | 예열 필요(JIT) | 즉시 최고 속도 |
| 가비지 컬렉터 멈춤 | 1ms 이하 | 설정에 따라 다름 | 없음 |
| 동시 처리 | 고루틴(개당 약 2KB) | 스레드 풀 또는 가상 스레드 | async 런타임 |
| 배우는 난도 | 낮음 | 중간(프레임워크가 큼) | 높음 |
| 빌드 속도 | 빠름 | 중간 | 느림 |
| 애플 공식 서버 라이브러리 | 없음 | 있음 | 없음 |
| 구글 공식 클라이언트 | 있음(`androidpublisher`) | 있음 | 확인 안 함 |
| 한국 채용 시장 | 작음 | 가장 큼 | 매우 작음 |

- 메모리와 난도 칸은 일반적으로 알려진 수준. 직접 잰 값 아님

### Java를 안 고르는 이유

- 서버 메모리: Spring은 아무 일도 안 해도 수백 MB. 서버 메모리가 Go를 고른 원래 이유
- 지금 서버가 이미 Go. V18까지 쌓인 서버를 다시 짜야 함
- Java 자체는 결제에 부족함 없음
  - 애플·구글 공식 라이브러리 모두 있음
  - 한국어 예제 가장 많음
  - 서버를 아직 안 짰고 메모리가 넉넉했다면 Java가 더 무난했을 것

### Rust를 안 고르는 이유

- Rust의 장점(멈춤 없음, 메모리 최소)이 필요한 일이 아님
  - 우리 서버는 DB와 스토어 응답을 기다리는 시간이 대부분. 언어 속도가 안 드러남
- 배우고 빌드하는 데 시간이 더 듦. 2명이 운영하는 단계에서는 손해가 큼
- 애플 공식 라이브러리가 없는 약점은 Go와 같음. 얻는 것 없이 비용만 늚

## 부록 B. 실제 기업이 결제에 Go를 쓴 이유

각 회사가 직접 쓴 글에서 옮김.

### American Express (카드 결제망)

- 2016년 말 결제 플랫폼을 새로 지으며 4개 언어 비교: C++17, Java, Node.js, Go
- 비교 방법: 같은 프로그램(카드 결제 전문 ISO8583을 JSON으로 변환)을 각 언어로 작성
- 사내에서 안 쓰던 언어는 Go뿐이었음
- 결과와 이유
  - 성능: 초당 14만 건으로 2위. 1위는 16만 7천 건
  - 예열 불필요: 서버가 뜨는 즉시 최고 속도
  - 가비지 컬렉터 멈춤: 운영에서 250µs~1ms. 별도 튜닝 없이 나온 값
  - 학습: 다른 언어를 쓰던 개발자가 1~2개월 안에 Go 프로젝트에 기여
  - 오류 처리: 오류를 무시한 코드(`v, _ := something()`)가 코드 검토에서 바로 보이고 도구로도 잡힘
  - 동시 처리: OS 스레드 최소 1MB, 고루틴 2KB. 스레드 풀 관리 불필요
  - 빌드: 비슷한 프로젝트의 절반 이하
- 2025년 후속 글
  - 짧은 멈춤과 고루틴이 저지연·대규모 결제 플랫폼에 맞음
  - 자원을 적게 써서 인프라 비용 감소
  - 사내 Go 개발자 약 1,000명
  - 어려웠던 점: 고루틴 정리와 조율

### PayPal (결제 플랫폼)

- 계기: 결제 처리 플랫폼의 핵심인 자체 NoSQL DB가 C++로 돼 있었음. 복잡해져 고치기 어려워지자 Go로 재작성
- 이유: 코드가 단순함. 고루틴과 채널로 동시 처리를 다루기 쉬움
- 결과: CPU 사용량 약 10% 감소. 코드 유지보수가 쉬워짐
- 한계: 주력 언어는 여전히 Java와 Node. Go는 주로 인프라에 사용

### MercadoLibre (남미 커머스, 결제 플랫폼 MercadoPago 포함)

- 계기: 기존 Groovy/Grails가 한계에 옴
  - 동적 언어라 성능을 내려면 숙련자의 튜닝이 필요
  - 테스트·빌드·배포가 느림
- 결과
  - 한 서비스의 서버 32대 → 4대
  - 서버당 CPU 4코어 → 2코어
  - 한 서비스는 메모리 20MB로 장비당 7만 요청 처리

### 공통점

1. 응답 시간이 일정함 (멈춤 1ms 이하, 예열 없음)
2. 동시 처리가 가벼움
3. 서버 수와 CPU가 실제로 줄었음
4. 실패를 무시한 코드가 눈에 보임
5. 사람을 빨리 투입할 수 있음

- 이 회사들도 Java를 버리고 전부 Go로 간 것은 아님
- 정확한 표현: "새로 짓는 고성능 결제 시스템에 Go를 골랐다"

### Go에서 Rust로 간 사례

- Discord: 읽음 상태 서비스. 가비지 컬렉터 때문에 약 2분마다 CPU가 튀어 Rust로 옮김 (2차 자료로만 확인)
- Dropbox: 저장 장비 소프트웨어. 메모리를 더 줄이려고 옮김 (2차 자료로만 확인)
- 둘 다 회사 전체가 아니라, 멈춤이나 메모리가 문제 되는 특정 서비스 하나를 옮긴 경우

## 부록 C. `awa/go-iap` 검토 (2026-11-18 확인)

### C-1. 왜 필요한가

- 애플 공식 서버 라이브러리: Swift, Java, Python, Node만 있음. Go 없음
- 구글 공식 클라이언트: Go 있음 (`google.golang.org/api/androidpublisher/v3`)
- `go-iap`은 애플 쪽 빈자리를 메우고 구글 공식 클라이언트도 감싸서 같이 제공

### C-4. 서명 검증

- 위치: `appstore/cert.go`
- 하는 일
  - 인증서 3장(리프, 중간, 루트)을 꺼냄. 3장이 아니면 거부
  - 내장된 Apple Root CA G3까지 체인 검증
  - App Store 서명용 표식(OID) 확인: 리프 `1.2.840.113635.100.6.11.1`, 중간 `1.2.840.113635.100.6.2.1`
  - 리프 공개키로 서명 확인
- 안 하는 일
  - 인증서 폐기 확인(OCSP)
  - 번들 ID·환경 비교 (읽은 범위에서는 없음)

### C-5. 알려진 문제

#### 서명 위조 (#348) — 수정됨

- 대상: v1.59.0 이하
- 원인: 인증서가 애플 루트로 이어지는지만 보고 App Store 서명용인지는 안 봄
- 공격 방법: 개발자 계정으로 발급받는 Apple Pay용 인증서도 같은 루트로 이어짐. 그걸로 서명한 가짜 거래·알림이 통과
- 재현: 보고자가 만료일이 먼 미래인 가짜 구독 알림을 통과시킴
- 수정: 11월 10일 보고 당일 v1.59.1
- 남은 것: OCSP, 유효일 확인은 안 들어감
- GitHub 보안 권고로 등록 안 됨. `govulncheck`에 안 잡힐 수 있음

#### 구글 클라이언트 변경으로 빌드 실패 (#341) — 수정됨

- 구글이 옛 구독 타입을 삭제해 v1.56.0 빌드가 깨짐. 당일 v1.57.0에서 수정
- 구글 클라이언트 버전을 올릴 때 `go-iap`도 같이 올려야 함

#### 샌드박스·운영 혼동 (#315, #283, #277)

- 샌드박스 거래를 운영 주소로 조회하면 실패. 심사와 TestFlight 구매가 해당
- `NewStoreClientWithSandboxFallback`을 쓰면 해결됨

### C-6. 서버에 미치는 영향

### C-8. 문제가 나면 피해가 어디까지 가는가

돈과 카드 정보는 스토어가 쥐고 있음. 위조로 우리 돈이나 유저 돈이 빠져나가지는 않음.

| 경로 | 피해 | 심각도 |
|---|---|---|
| 영수증 위조 | 결제 없이 구독·선반 획득 | 낮음. 원가가 드는 상품이 아님 |
| 위조 방법 공유 | 여러 명이 무료 이용 | 중간. 매출 기회 손실 |
| 가짜 환불·만료 알림 | 돈 낸 유저의 구독 해제 | 중간. 피해자가 정상 유저. 단 거래 ID를 알아야 함 |
| 영수증 돌려쓰기 | 구매 하나를 여러 계정이 사용 | 유일 제약과 계정 묶기로 차단 |
| 환불 후 계속 사용 | 환불받고 상품 유지 | 환불 알림 처리로 차단 |
| 알림 주소 도배 | 스토어 API 할당량 소진, 정상 검증 지연 | 결정 10으로 완화 |
| 구글 확인(acknowledge) 누락 | 3일 뒤 자동 환불. 정상 유저가 구매를 잃음 | 공격이 아니라 장애 |
| **스토어 키 유출** | 구글: 환불·구독 취소 API 호출 가능. 애플: 거래 조회, 구독 갱신일 연장 | 높음. 실제 매출이 걸림 |

- 피해가 작은 이유: 상품을 되팔거나 남에게 넘길 수 없음. 서버에 카드 정보 없음
- 커지는 조건: 코인, 선물하기, 유저 간 거래를 넣는 경우. 위조 구매가 현금화 수단이 됨
- 애플에는 환불 실행 API가 없음. 환불은 애플이 결정
- 따져 본 범위: 라이브러리 코드와 스토어 API 문서 기준. 공격을 재현해 보지는 않음

## 부록 F. 웹 프레임워크: 표준 `net/http` 유지 (2026-11-26)

- 결정: Gin·Echo·Fiber를 들이지 않고 지금처럼 표준 `net/http`의 `ServeMux`를 쓴다(범수)
- 근거
  - Go 1.22부터 표준 라우터가 메서드 구분과 경로 변수를 지원한다. Go 팀이 서드파티 프레임워크에서 가장 많이 쓰는 기능을 골라 넣었다
  - 우리 서버는 Go 1.27, 라우트 27개, 대부분 DB와 스토어 API를 기다린다. 2026년 벤치마크에서 Gin·Echo·표준 라우터의 처리량은 몇 % 차이라 이점이 묻힌다
  - 오류 처리 감싸기(`wrap`)와 제출 횟수 제한은 이미 함수로 있다
  - 옮기면 핸들러와 결제 시험을 전부 다시 손봐야 한다
- 고르지 않은 것
  - Gin: 가장 많이 씀(2025 JetBrains 조사 48%). 핸들러가 `gin.Context`에 묶인다. 새 프로젝트라면 무난하지만 옮길 이유가 없다
  - Fiber: 가장 빠르지만 HTTP/2를 지원하지 않고(fasthttp 설계와 충돌), 요청 객체를 다음 요청에 재사용한다. 핸들러가 끝난 뒤 값을 붙잡으면 다른 요청과 섞인다. 커밋 뒤 확인·환불을 뒤에서 처리하는 결제 코드에 위험하다. 표준 핸들러와 호환되지 않는다
  - 참고 규모: 바이트댄스는 Gin을 감싸 쓰다가 서비스 1만 개, 최고 초당 4천만 요청 규모에서 자체 프레임워크(Hertz)로 옮겼다(자체 발표 수치)
